# SultiAI auth email templates

Branded Supabase Auth emails for SultiAI: signup confirmation, password
recovery, invitation, magic link, email change, reauthentication, and the
password-changed security notification.

## Design

- Table-based layout with inline CSS; no JavaScript or external stylesheets.
- No remote images, so the layout renders without "download images" prompts.
- Palette: navy `#0A121D`, teal `#00B8A9`, ink `#0F172A`.
- Accessible teal CTA (`#00B8A9` with `#04211F` text).
- Every action URL is generated by Supabase (`{{ .ConfirmationURL }}`).
  Reauthentication uses `{{ .Token }}`.
- Includes a copy/paste fallback link and security guidance.

## Build

```bash
node supabase/email-templates/build.mjs
```

This writes `confirmation.html`, `recovery.html`, `invite.html`,
`magic_link.html`, `email_change.html`, `reauthentication.html`,
`password_changed_notification.html`, and `subjects.json`. Edit `build.mjs`
(not the generated HTML) and rebuild.

Supabase keeps the password-changed notification disabled by default
(`mailer_notifications_password_changed_enabled = false`). The branded content
is ready; an admin can enable it after the sending domain is verified.

## Push to Supabase

The Supabase Dashboard does not expose the full HTML through a project file.
Use the Management API:

```bash
export SUPABASE_ACCESS_TOKEN="sbp_..."      # never commit this
export SUPABASE_PROJECT_REF="pptanwtuybivlqeyntwh"
node supabase/email-templates/push.mjs
```

Or paste each generated file into **Supabase Dashboard → Authentication →
Emails** under the matching template. The dashboard and the API update the
same hosted configuration.

## SMTP provider

Supabase Auth sends these emails through custom SMTP, configured in
**Supabase → Authentication → Emails → SMTP Settings**. It is not read from
this repo, and `supabase/config.toml` leaves `[auth.email.smtp]` commented out
because that file only drives the local stack.

The hosted project was configured with Resend:

| Setting | Value |
| --- | --- |
| Host | `smtp.resend.com` |
| Port | `465` |
| Username | `resend` |
| Password | Resend API key (stored in Supabase, never in this repo) |
| Sender name | `SultiAI` |
| Sender email | `onboarding@resend.dev` (testing) |

`onboarding@resend.dev` is Resend's test sender: it only delivers to the Resend
account owner, so password-recovery and confirmation emails fail for every
other learner (Supabase turns that into `Error sending recovery email`).

Until a domain is verified in Resend, the project uses Gmail SMTP instead:

| Setting | Value |
| --- | --- |
| Host | `smtp.gmail.com` |
| Port | `465` |
| Username | the full Gmail address |
| Password | 16-character Google App Password (requires 2-Step Verification) |
| Sender name | `SultiAI` |
| Sender email | the same Gmail address |

Gmail delivers to any recipient without domain verification, but it is meant
for demos: roughly 500 recipients/day, a `@gmail.com` From address, and Google
Workspace admins can disable App Passwords entirely.

### Before production: verify a domain in Resend

Resend's test sender only delivers to the Resend account owner's address.
To email learners (and leave Gmail behind):

1. Add a domain at <https://resend.com/domains> (for example `sultiai.com`).
2. Add the DNS records Resend shows (SPF, DKIM, and DMARC where applicable).
3. Wait for **Verified** status.
4. In Supabase Auth → Emails → SMTP Settings, switch the host back to
   `smtp.resend.com`, username `resend`, the Resend API key as the password,
   and set the sender email to an address on the verified domain
   (for example `no-reply@yourdomain.com`).
5. Re-test signup confirmation and password recovery.

Do not bypass this restriction by disabling email confirmation or using a
fake sender address.
